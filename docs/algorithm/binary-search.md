# 二分查找：让搜索区间持续减半

一排数字卡片已经从小到大放好。你要找 `9`，翻到中间却是 `3`，还需要查看左边的每张卡片吗？有序性让你一次排除一段位置，但边界挪错一步，就可能漏掉答案或让循环停在原地。

> **环境与安全**：先掌握 JavaScript 函数、数组下标、循环与条件判断。沙盒仅运行同步 JavaScript，不是 Node.js；不支持 npm、import、网络、DOM、IndexedDB、文件系统、后端或真实 Linux。只有点击运行才执行，不自动载入远端代码、不保存草稿、不收集遥测。不要输入秘密或不明来源代码。编辑器需要客户端 JavaScript，正文与参考代码可静态阅读。

> - 从小到大排列的卡片 → 严格递增、无重复的数组 `nums`。
> - 卡片的固定编号 → 原始数组下标，找到后返回这个编号。
> - 两端的标记 → 闭区间 `[left, right]`，两端都是待查位置。
> - 翻看中间卡片 → 比较中点值与 `target`，排除不可能包含目标的一半。

比喻依赖卡片已经有序，不能把无序卡片直接当作二分查找的输入。完成本页后，你应能独立维护闭区间，解释每次循环为什么推进，以及空数组和未找到为何统一返回 `-1`。

## 一、先把题意说准确

编写同步函数 `function binarySearch(nums, target)`。给定严格递增、没有重复元素的整数数组 `nums` 和整数目标值 `target`，返回目标在原始数组中的下标；如果目标不存在，返回数值 `-1`。

- 下标从 `0` 开始，找到时返回单个 `number` 类型的整数，不是目标值本身。
- `0` 是合法下标；`"0"` 和 `[0]` 不是本题答案。未找到返回 `-1`，不是 `"-1"`、`[]` 或 `undefined`。
- 数组可以为空，也可以只有一个元素。没有重复值，因此不需要约定返回第一个还是最后一个重复位置。
- **不要直接排序输入**。题目已保证有序，排序是多余工作；对无序输入先排序还会改变原始下标含义，不属于本题契约。
- 直接返回答案，不写 `export` 或 `module.exports`，不使用 `async`、Promise 或其他 thenable。参数与返回值还须遵循[通用 JSON 契约](./#同步函数契约)。

本题使用普通 JSON 精确比对：实际返回的类型和值都必须与期望一致。两数之和允许交换两个下标的规则不适用于本题。

### 本题的 7 个固定用例

| 用例 | `nums` | `target` | 期望返回 | 要检查的边界 |
| --- | --- | --- | --- | --- |
| 首元素也是左邻 | `[5, 6, 7]` | `5` | `0` | 首元素同时是首个中点左边一位，检查 `right` 是否少跳 |
| 命中内部元素 | `[-1, 0, 3, 5, 9, 12]` | `9` | `4` | 答案在内部，不必是第一次选择的中点 |
| 末元素也是右邻 | `[5, 6, 7]` | `7` | `2` | 末元素同时是首个中点右边一位，检查 `left` 是否多跳 |
| 目标不存在 | `[1, 3, 5, 7]` | `4` | `-1` | 目标夹在相邻值之间也可能不存在 |
| 空数组 | `[]` | `3` | `-1` | 初始区间就为空 |
| 单元素命中 | `[8]` | `8` | `0` | `left === right` 时仍需检查 |
| 单元素未命中 | `[8]` | `2` | `-1` | 排除最后一个位置后结束 |

## 二、用闭区间写出初始解法

`[left, right]` 表示两端都包含的待查范围：初始左端为 `0`，右端为 `nums.length - 1`。只要 `left <= right`，就至少有一个位置还没有排除。

编辑器的初始代码如下，按题意应通过全部 7 例。

```javascript
function binarySearch(nums, target) {
  let left = 0
  let right = nums.length - 1
  while (left <= right) {
    const middle = left + Math.floor((right - left) / 2)
    if (nums[middle] === target) return middle
    if (nums[middle] < target) left = middle + 1
    else right = middle - 1
  }
  return -1
}
```

这里的 `middle` 就是常写作 `mid` 的中点。用 `left + Math.floor((right - left) / 2)` 取靠左的中间下标。不要用 JavaScript 位移运算简写中点：位运算会把数值转换为 32 位整数，对较大下标可能产生截断或符号问题。

**操作**：保持初始代码并点击运行。**观察**：逐例核对输入、期望、实际与状态，预期 7 例全部通过；重点看首/末元素如何同时检查 `right = middle - 1` 与 `left = middle + 1` 是否跳过相邻位置，以及空数组、单元素和缺失用例。**原理**：命中就返回编号，没有命中就排除已确认不可能的部分，直到区间为空。

## 三、每次都要排除已经检查的中点

以第一例的数组和目标 `9` 为例，手工推演如下。这是按源码展开的预期过程，不是浏览器运行记录。

| 循环开始的区间 | `middle` | 中点值 | 比较与下一步 |
| --- | --- | --- | --- |
| `[0, 5]` | `2` | `3` | `3 < 9`，下标 `0` 到 `2` 都不可能，令 `left = 3` |
| `[3, 5]` | `4` | `9` | 命中，返回下标 `4` |

为什么更新为 `left = middle + 1`，而不是 `left = middle`？因为 `nums[middle] < target` 已经证明中点也不是答案。相反，若 `nums[middle] > target`，中点及右边都不可能，必须令 `right = middle - 1`。

用不变量检查正确性：**若目标存在，它的下标始终位于当前闭区间内**。

1. 初始区间覆盖整个数组，不会漏掉目标。
2. 数组严格递增。中点值偏小时，左侧值更小，可以安全排除；偏大时同理排除右侧。
3. 没有返回时，新区间严格缩小；即使只剩一个元素，也会命中或将它排除，不会停在原地。
4. 最终 `left > right` 时没有剩余候选位置，返回 `-1`。

空数组一开始就是 `left = 0`、`right = -1`，循环不执行。单元素区间是 `[0, 0]`，因此循环条件必须包含等号。这两个边界都不需要单独增加特判。

## 四、一次只改一处，观察边界错误

每次从初始代码开始，实验后点击重置，再进行下一项。仍使用上面的同一个沙盒，不需要额外教学控件。

| 操作 | 预期观察 | 原理 |
| --- | --- | --- |
| 将 `left <= right` 改为 `left < right` | 单元素命中等用例失败 | 最后一个候选位置没有被检查 |
| 将 `return middle` 改为 `return nums[middle]` | 命中用例出现答案错误 | 需要卡片编号，不是卡片值 |
| 将 `return middle` 改为 `return String(middle)` | 命中用例答案错误 | 精确比对不把字符串转换成数值 |
| 将末尾 `return -1` 改为 `return []` | 目标不存在、空数组和单元素未命中失败 | 两道题的返回形式不能混用 |
| 将 `left = middle + 1` 改为 `left = middle` | 命中末元素等用例可能卡住；可点击停止，否则等待超时 | 区间只剩相邻位置时，中点可能一直等于左端，区间不再缩小 |

最后一项会故意造成不推进的循环，只在本地教学沙盒内练习，并及时停止。停止保留已完成结果；后续未执行用例不能算成通过或失败。重置会终止运行、恢复初始代码并清空结果。

你也可以在循环内加入少量 `console.log(left, right, middle)`，观察区间变化，再删除日志重新运行。日志消耗输出预算；不要用日志条数或一次页面耗时替代复杂度分析。

## 五、为什么是对数时间与常量空间

令 `n` 为数组长度。每次没有命中时，保留的候选位置至多约为原来的一半。连续减半直到没有候选位置，循环次数随 `log₂ n` 增长。

| 项目 | 复杂度 | 依据 |
| --- | --- | --- |
| 最坏时间 | `O(log n)`，针对非空数组的渐近分析 | 每轮常数次访问与比较，候选区间不断减半 |
| 最好时间 | `O(1)` | 第一次比较就命中；空数组也以常数工作结束 |
| 额外空间 | `O(1)` | 迭代实现只维护左右端点和中点，不计输入与执行器开销 |

若要把 `n = 0` 也写进统一的上界，可写作 `O(log(n + 1) + 1)`。这里的空间分析针对上述迭代函数，不是整个编辑器或 Worker 的内存占用；若改成递归，还需要计入调用栈。

题目已经保证有序，不应先排序再宣称整个算法只有对数时间。固定小样例也不是性能基准，页面上的一次耗时包含执行与输出处理等开销，不能据此宣布比线性查找快了多少倍。
