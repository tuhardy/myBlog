# 消息队列基础：RabbitMQ vs Kafka

> 什么时候该引入 MQ？应用场景、术语与选型对比


## 为什么要引入 MQ

三大收益：
1. **异步**：把耗时的发短信、发邮件丢给消费者，主流程秒返回
2. **解耦**：订单系统只负责发消息，不关心谁消费
3. **削峰**：大促流量先进队列，下游按自己节奏慢慢吃

## 术语一张表

| 术语 | 说明 |
|---|---|
| Producer | 生产者，发消息 |
| Consumer | 消费者，收消息 |
| Broker | MQ 服务本身 |
| Topic / Queue | 存放消息的逻辑容器 |
| ACK | 消费确认，防止丢消息 |

## RabbitMQ vs Kafka

| 维度 | RabbitMQ | Kafka |
|---|---|---|
| 模型 | 队列 + Exchange 路由 | 分布式日志（分区） |
| 吞吐 | 万级 | 十万 / 百万级 |
| 延迟 | 微秒级 | 毫秒级 |
| 适合场景 | 业务异步、RPC | 日志、埋点、大数据 |

简单理解：**业务用 Rabbit，数据用 Kafka**。

::: danger 三大坑
- 消息丢失（开启持久化 + 手动 ACK）
- 重复消费（消费者必须做到幂等）
- 消息积压（消费者扩容 / 丢弃非关键消息）
:::
